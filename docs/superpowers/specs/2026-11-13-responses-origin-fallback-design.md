# Responses 来源无法解析时继续转发

## 已确认目标

用户已确认：Responses 来源过期、不存在、无效或 Redis 读取失败时，按当前分组、模型及渠道能力选渠并允许后续继续请求，不再由来源检查直接返回 409/503。保留正文和旧 ID，交给上游验证历史；新请求成功只登记新响应来源，旧映射按原 TTL 保留。2026-11-13 用户要求开始实施。

## 方案与范围

- 仅补 `additional_tools` / `agent_message` 白名单仍会遗漏其它回放及服务端引用，也不能覆盖 Redis 故障，不满足最终要求。
- 延长 TTL 或持久化来源可减少来源丢失，但无法恢复已丢失记录，且超出本次选定范围。
- 采用：`/v1/responses` 和 `/v1/responses/compact` 的来源查询失败均退回正常选渠；删除这两个端点的回放形态白名单，使用与已知来源请求相同的正文校验/透传链路。

## 行为约束

1. 来源已知时继续遵守原类型、区域、key 和模型/分组权限。已知来源无可用渠道不能借本修复扩大范围。
   来源回退直接走校验模型能力的随机选渠，跳过规则亲和缓存及其禁止重试标记，避免命中模型能力已禁用的渠道。
2. 来源查询错误分类保留：`not_found`、`unavailable`、`invalid`。记录到运行日志及现有日志的 `responseCorrelation.origin_lookup_status`；不把读取故障伪称为确实不存在，不记录请求正文或密文。
3. 放行只清除本次选渠提示，保留 `previous_response_id`、`X-Response-ID`、input、加密内容及历史关联 ID。不静默删改历史，不绑定旧 ID 到新渠道。
4. 分发使用入口已取得的来源快照，不再重复查询。一次请求已经采取来源回退后，重试不能因再次读取 header 来源而突然改变约束，或把恢复后的来源冒充本次已验证的父来源。
5. 上游验证 `additional_tools`、`agent_message`、服务端引用、compaction 和未知项；上游失败沿用现有 HTTP 状态、错误消息和失败日志，不伪造成功。现有 HTTP 错误包装的 `status_<http>` code 不在本次改变。来源回退请求禁用 Azure 删除加密历史的降级重试；其它请求保持原行为。入口已有格式/模型校验及 header/body ID 冲突检查保持有效。
6. 继续使用现有有限重试次数、超时及首次选渠后的重试约束；允许多次客户端请求不代表单次请求无限循环。
7. 新响应登记沿用原流程；Redis 故障不影响转发，但无法保证故障期间新来源登记成功。旧映射不删除、不改绑、不续期。
8. Chat/Gemini/Claude 的来源和签名策略、TTL、数据库结构和线上配置不在本次修改范围。

## 验证

用 Gin 分发、SQLite 渠道、miniredis 和本地 HTTP 上游验证：扩展历史在来源存在和过期后多次转发；服务端引用交由上游拒绝；Redis 读取错误/停用/连接失败仍可选渠；Redis 恢复不改变本次重试的来源认定；已知来源约束和原映射保持；success/error 日志保留 fallback 原因；仅新 ID 登记。

执行针对性及 race 回归、`go build ./... && go vet ./...`、`go test ./...`。全量既有失败与基线逐项核对。完成独立审阅与提交，本次不推送或部署。
