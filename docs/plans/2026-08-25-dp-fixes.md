# 动态优先级选渠道链路修复（修法 A + 探索 slots + 成功率平滑）

## 一、背景

当前 `dynamic-priority` 分支上线后，通过生产 DB 抽样验证发现三个致命问题：

1. **选渠道 SQL 兜底方向反了（Bug A）**：`model/cache.go:584` 用
   `COALESCE(NULLIF(dynamic_priority, 0), priority) DESC` 排序。静态 `priority` 默认 100，
   `dynamic_priority` 满分 100。**dp=0（未评分）走静态兜底 100 → 排在所有真实评分（1~90）之前**。
   评分识别为"较好"的渠道反而永远排在"未评分"之后。

   量化：全库 735 条 dp>0 记录，进入选渠道 top 10% 的 **0 条**（0.0%）。评分系统对
   实际选渠道**没有任何影响**。举例：`gemini-3.1-flash-image` dp=90 的渠道排第 74/85 名；
   `gpt-4.1-nano` 最高分 dp=50 排 803/803，倒数第一。

2. **新加/低样本渠道没有探索机制**：修 A 后 dp>0 永远优先，dp=0 拿不到流量 → 永远评不
   上分 → 系统被"评过分的先跑者"锁定，冷启动失效。

3. **持续 429 但仍显示未评分（Bug B）**：`hasEnoughData` 门槛是 `TotalCount >= 20`。
   一个渠道 window 内 15 次全 429（<20 样本），因失败样本 duration=0、first_word=0，
   `hasEnoughData=false` → dp 被写 0 → 叠加 Bug A 后被 static priority=100 兜底 →
   **总是被首选** → 又是 429 → 恶性循环。`scoreSuccess` 里小样本回退 midScore=50 更加剧
   这一点：全失败但样本少的渠道被评为"中等"。

## 二、目标

- **修 Bug A**：让评过分的渠道排在未评分之前，恢复评分对选渠道的实际影响力
- **给新加渠道快速评分机会**：top 档预留 K 个探索位，优先塞给最新加入的 dp=0 渠道
- **修 Bug B**：用 Beta-Binomial 平滑处理小样本成功率，让"全失败但样本少"的渠道自然
  拿到低分而不是"未评分"

不在本次范围内（进入待实现列表）：
- **重试链梯度参数化**（问题 4）：`selectByDynamicPriority` 接受 `(retryIndex, maxRetry)`
  按可变 N 生成扩档序列，落地后单独 PR

## 三、方案设计

### 3.1 修法 A：SQL 兜底方向

`model/cache.go` 中 `selectByDynamicPriority` 的 ORDER BY 改为按下列优先级排序：

```sql
ORDER BY
  (CASE WHEN abilities.dynamic_priority > 0 THEN 1 ELSE 0 END) DESC,  -- 有评分排前
  abilities.dynamic_priority DESC,                                     -- 评分高排前
  (CASE WHEN abilities.dynamic_priority = 0 
        AND channels.created_time > $NOW_MINUS_TTL 
        THEN 1 ELSE 0 END) DESC,                                       -- 未评分池内，24h 内新加的排前
  channels.created_time DESC,                                          -- 新加渠道排前
  abilities.priority DESC                                              -- 传统静态优先级兜底
```

- 主排序键：`dp > 0` 二值分档，把"有评分"和"未评分"硬拆开
- 次排序键：`dp DESC`，评分高的优先
- 未评分池内部：24h 内新加的排前 + created_time 递减，让最新的排在最前面
- 最终兜底：`abilities.priority`

同时增加返回列 `dp`，Go 层用它拆 scored / unscored 池。

### 3.2 方案 1：探索位 slots

`selectByDynamicPriority` Go 层：

```
1. SQL 按上面 ORDER BY 查回所有 enabled 渠道（含 dp 字段）
2. 拆分：scored = 有 dp>0 的部分（已按 dp DESC 排好），
        unscored = 剩余 dp=0 的部分（已按 created_time DESC 排好）
3. 计算 topCount = max(1, len(scored) * TopThreshold%)
4. 计算 exploreCount = min(ExploreSlots, len(unscored))
   重试时（skipPriorityLevels > 0）exploreCount 置 0：重试是错误恢复，不做探索
5. tier = scored[skip : skip+topCount] + unscored[:exploreCount]
6. tier 内 weight 加权随机（原逻辑不变）
```

**为什么探索位从"最前面"取，而不是随机抽**：
- unscored 已按 `created_time > now-TTL` DESC 再按 `created_time DESC` 排序
- 前 K 个 = 最新加入的 K 个 dp=0 渠道
- 超过 24h TTL 的老 dp=0 渠道排到 unscored 后半段，抽不到 K 位 → 不再被优待
- TTL 兜底避免"某渠道就是烂，一直凑不齐样本，一直占 K 位"

**为什么重试时关闭 exploreCount**：
- 首选保 SLO：主档 90% 命中率的话，K=2 探索位只影响 10% 首选，用户体验损失可控
- 重试链是错误恢复：探索代价此刻由用户体验承担，不合理

### 3.3 Beta-Binomial 成功率平滑

`common/dynamicprio/score.go`：

```go
const (
    priorAlpha = 2.5  // 虚拟成功样本数（先验）
    priorBeta  = 2.5  // 虚拟失败样本数（先验）
)

// scoreSuccess 用 Beta-Binomial 平滑代替硬阈值 MinSampleCount 分支
smoothed := (SuccessCount + priorAlpha) / (TotalCount + priorAlpha + priorBeta)
score := smoothed * 100
```

对照效果：

| 场景 | 平滑成功率 | 得分 | 语义 |
|---|---:|---:|---|
| 0 成功 / 5 失败 | 2.5/10 | **25** | 小样本负面信号，给低分不给中位分 |
| 0 成功 / 20 失败 | 2.5/25 | **10** | 大样本负面，接近真实成功率 0% |
| 5 成功 / 5 失败 | 7.5/15 | 50 | 5:5 信号中立 |
| 100 成功 / 0 失败 | 102.5/105 | 97.6 | 大样本正面，接近真实 |
| 0 样本（真无数据） | 2.5/5 | 50 | 完全无数据 → 中位分（与原兜底一致） |

`hasEnoughData` 相应放宽：

```go
func hasEnoughData(s ChannelStat) bool {
    return s.TotalCount > 0 || s.AvgLatencyMs > 0 || s.AvgFirstTokenMs > 0
}
```

有任何请求样本或延迟数据即视为有数据。这样 15 次全 429 的渠道 → `HasData=true` →
写入平滑后的低分（约 15~25 分，而非 0）→ 选渠道排在 dp=0 前面 → 但排在正常渠道之后。

`MinSampleCount` 常量保留（用于文档），但不再是硬门槛。

## 八、code review 修正（首次落地后审计发现）

首次实现落地后 code review 发现三个方向性 bug，一并修复。**改动都在同一批落地内，未单独 commit**，此处记录以便回溯。

### P1 #1：TTL 未真正限制探索位

**问题**：SQL 层 `ORDER BY` 只保证"created_time > TTL 的新加渠道排前"，Go 层 `unscored[:K]`
无脑取前 K —— 若 unscored 池里**没有**任何 TTL 内新渠道，会误取到老 dp=0 渠道，让它们
长期占用探索位。违背 plan 里"超过 24h 抽不到 K 位"的语义。

**修法**：Go 层显式过滤 `unscored[i].CreatedTime > ttlThreshold` 得到 `freshUnscored`，
探索位只从 `freshUnscored` 里取。若无任何 fresh 渠道，`exploreCount = 0`，纯走主档。

**代码位置**：`model/cache.go` `selectByDynamicPriority` 里 `freshUnscored` 段。

### P1 #2：SQL ORDER BY 未处理 NULL（PG 上翻车）

**问题**：`abilities.dynamic_priority` 字段类型 `*int64`（可 NULL）。虽有 `default 0`，
但历史行可能是 NULL。`SELECT` 层的 `COALESCE(dp, 0) AS dp` 只覆盖 Go 拆池；`ORDER BY`
表达式独立求值，仍用裸 `abilities.dynamic_priority`。**PG DESC 下 NULL 排最前**，把老
NULL 渠道推到 unscored 池最前，抢占探索位；MySQL DESC 下 NULL 排最后碰巧不坏排序。

**修法**：所有排序表达式（含 CASE 分支）里的 `abilities.dynamic_priority` 全部替换为
`COALESCE(abilities.dynamic_priority, 0)`。SELECT 层的 `dp` 别名保留（供 Go 层拆池）。

**代码位置**：`model/cache.go` `selectByDynamicPriority` 里 `orderClause` 段。

### P1 #3：探索位在重试时错误开启（连带发现）

**问题**：探索位判定用 `skip == 0`。项目里 `retry_policy.go:25-27` 的重试链**始终传
skip=0**（依靠 `excludeIds` 排除失败渠道）。这意味着每次重试都会重新塞入探索位 ——
把探索池当重试预算消费，违背"首选保 SLO、重试纯恢复"的设计意图。

**修法**：判定条件改为 `len(excludeIds) == 0 && skip == 0`。真正的首选（`middleware/
distributor.go:143` 调用时 excludeIds=[]）才开启探索；重试链（excludeIds 非空）关闭。

**代码位置**：`model/cache.go` `selectByDynamicPriority` 里 `exploreCount` 判定段。

### 审计过但没问题的场景

- **auto_disabled 隔离**：`WHERE abilities.enabled=1 AND channels.status=Enabled` 已覆盖
  ability 级 auto_disabled 和渠道级手动禁用/自动禁用（`abilities.enabled` 由后台同步
  维护，反映 `(channel.status, ability.auto_disabled)` 组合状态）
- **稀疏流量抖动**：`hasEnoughData` 放宽后，稀疏流量渠道会在"有请求给高分" vs "窗口滑出
  给 0 分" 之间摆动。这是原代码固有行为（`if !HasData { dp=0 }`），不是本次回归
- **重试链无限循环**：`selectRetryChannel` 内部 reset 只做一次，`for i := retryTimes` 有
  终止条件，最坏情况耗尽重试次数正常退出
- **Beta 数据一致性异常**：`SuccessCount > TotalCount` 之类的数据脏，输出被 clamp 到
  [0, 100]，不会溢出
- **新配置异常值**：负数被 `setPositiveIntOption` / `if v >= 0` 拦截，保持默认值
- **PG NULL 拆池**：`SELECT COALESCE(dp,0) AS dp` 保证 Go 层 `rows[i].Dp > 0` 判定对
  NULL 也正确；配合 P1 #2 的 ORDER BY 修复，PG 上行为与 MySQL 一致

## 九、上线后性能与前后端一致性修复

首次落地后生产日志显示单轮评分实际耗时约 **322 秒**（用户配置评分周期 1 分钟，
但相邻两轮实际间隔 ≈ 322s，说明单轮跑不完 1 分钟）。同时发现展示层排序仍是原
COALESCE bug，与选渠道排序不一致。

### 性能坑：priceCache 作用域错了

**根因**：`controller/dynamic_priority.go` 里 `buildStatsForModel` 的 `priceCache` 是
**每个 model 建一份的局部变量**。同一 channel 出现在 N 个 model 下会被 `GetChannelById`
DB 直查 N 次（`GetChannelById` 走 `DB.First`，不走 MemoryCache）。

生产数据估算：
- 62,357 distinct enabled channels
- 544 distinct models
- 平均一个 model 300 channels
- 总查询数 ≈ 544 × 300 = **163,200 次单条 SELECT**
- 阿里云 RDS RTT ~2ms → **~326 秒 ≈ 观察到的 322s**

**修法**：把 UnitPrice 批量拉取抽到 `runDynamicPriorityCalcOnce` 顶层：

```go
// runDynamicPriorityCalcOnce 一次性拉全部 enabled 渠道的 UnitPrice
priceCache := make(map[int]float64)
DB.Table("channels").
    Where("status = ?", ChannelStatusEnabled).
    Select("id, unit_price").
    Find(&priceRows)
// 传给 buildStatsForModel 复用
```

`buildStatsForModel` 签名新增 `priceCache map[int]float64` 参数，删掉内部
`GetChannelById` 调用。**16 万次 SELECT → 1 次批量 SELECT**，单轮耗时预期
从 322s 降到 10~30s。

**回退兜底**：批量 SELECT 失败时不中止评分，priceCache 空 → 价格维度回退到
中位分，成功率+延迟维度仍能正常评分（价格权重默认只有 20%，短暂失效影响小）。

**代码位置**：`controller/dynamic_priority.go` `runDynamicPriorityCalcOnce` +
`buildStatsForModel` 签名。

### 展示层 ORDER BY 与选渠道不一致

**问题**：`controller/dynamic_priority_view.go:ListModelChannels` 的 ORDER BY
用的还是 `COALESCE(NULLIF(a.dynamic_priority, 0), COALESCE(a.priority, 0)) DESC` ——
**修法 A 修掉的那个 Bug 的孪生版本**。运维在管理页面看到"A 排第一"，实际选渠道
按 `(dp>0) DESC, dp DESC` 打给 B，前后端错位。

**修法**：ORDER BY 对齐 `selectByDynamicPriority` 的主排序键：

```sql
(CASE WHEN MAX(COALESCE(a.dynamic_priority, 0)) > 0 THEN 1 ELSE 0 END) DESC,
MAX(COALESCE(a.dynamic_priority, 0)) DESC,
c.created_time DESC,                     -- 对齐探索位选取偏好
MAX(COALESCE(a.priority, 0)) DESC,
a.channel_id ASC
```

同时 `SELECT` 加 `c.created_time`，`ModelChannelItem` 新增 `CreatedTime` 字段。
前端可以基于 `dp=0 && created_time > now - 24h` 展示"探索位"标签，让运维一眼
看清哪些是新加渠道正被优待。

**代码位置**：`controller/dynamic_priority_view.go` `ListModelChannels` +
`ModelChannelItem` struct。

## 十、负载均衡与 429 秒级降权

上线后观察到：即使评分正确，高分渠道仍会被瞬时打满触发 429，dp 分数要等下轮评分
（1~2 分钟）才能下调，客户端在此期间体验到间歇性 429。根因不是"评分慢"，是
**选渠道过度集中**：`top X%` 档内按 `channel.weight` 等权分流，高分渠道天然拿最多流量。

### 方案 1：档内 `dp × weight` 加权随机

**问题**：档内所有渠道按静态 `channel.weight` 分流，dp=90 和 dp=50 的渠道流量比是 1:1
（甚至 weight 相同时均分）。最高分渠道拿到远超其容量的流量。

**修法**：`selectByDynamicPriority` 里档内加权公式改为 `weight × dp`（dp>0 时）：

```go
w := int(channel.Weight)
if t.Dp > 0 {
    w = w * int(t.Dp)  // dp=90 vs dp=50，流量比 1.8:1
}
```

**效果**：
- 高分渠道拿主流量，但不再垄断
- 低分但健康的渠道拿到零碎流量，天然分散负载
- 探索位（dp=0）保持基础 weight，不受影响

**代码位置**：`model/cache.go` `selectByDynamicPriority` 档内加权段。

### 方案 2：429 即时反馈层（60 秒短窗口）

**问题**：dp 评分是 10 分钟滑动窗口 + 每分钟评分的慢变信号，无法秒级反应"某渠道
刚开始被打爆"。选渠道后即使触发大量 429，dp 也要等下轮才更新。

**修法**：独立的 Redis 60 秒短窗口计数：
- 打点：`controller/relay.go` 失败路径 `err.StatusCode==429` 时调 `RecordRateLimit`
- 存储：`channel_recent_429:{channel_id}` Sorted Set，TTL 90s
- 读取：`selectByDynamicPriority` 里 tier 组成后**一次 pipeline** 批量 ZCount
  所有 tier 渠道，命中阈值（60s 内 ≥3 次 429）的渠道权重强制降到 1

```go
// 一次 pipeline 拿所有 tier 渠道的 429 计数
rateLimits := metrics.GetRecentRateLimits(ctx, tierChannelIds)

// 档内加权时降权
if rl, ok := rateLimits[t.Id]; ok && rl >= 3 {
    w = 1  // 短暂冷却
}
```

**语义**：
- 60s 内 <3 次 429：正常参与加权随机
- ≥3 次：权重降到 1，被选中概率极低但仍在池中兜底
- 60s 过去 rate limit 缓解，ZCount 自然归零，权重恢复

**为什么是独立系统而非扩展 ability_metrics**：
- `ability_metrics` 用于评分，需要区分成功/失败/延迟/流式等多维度信号
- 429 反馈只需一个"计数" —— schema 简单、读取快（ZCount 是 O(log N)）
- 独立系统失败不影响评分，评分失败也不影响 429 反馈

**代码位置**：
- 新增 `common/metrics/rate_limit.go`（`RecordRateLimit` + `GetRecentRateLimits`）
- `controller/relay.go` 失败路径 429 打点
- `model/cache.go` `selectByDynamicPriority` 档内降权

### 方案 1 vs 方案 2 的分工

| 场景 | 方案 1 生效 | 方案 2 生效 |
|---|---|---|
| 稳态负载分配 | ✅ 按 dp 比例分流 | 空转（无 429） |
| 某渠道刚开始过载 | 不直接干预 | ✅ 秒级降权 |
| 上游临时抖动 | 不直接干预 | ✅ 60s 内避开 |
| 长期健康度差异 | ✅ 通过 dp 反映 | 不直接干预 |
