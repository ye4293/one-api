# 上游模型同步真实请求探针

- **日期**: 2026-08-05
- **分支**: `upstream-model-probe`
- **类型**: feat + fix

## 一、背景与目标

### 问题

`controller/channel_upstream_update.go` 的定时巡检任务依赖上游 `/v1/models` 接口做模型列表同步：拉上游列表 → 与本地 `channels.models` 做 diff → 按开关自动增删。但 `/v1/models` 不可靠：

- **虚报**：列出实际调用会 404 的模型 → 被自动加进本地列表 → 用户请求直接失败
- **漏报**：不返回实际可用的模型 → 被自动从本地列表删掉 → 可用容量白白丢失

现状的防误删保护**只有两道**：

1. 上游返回空列表则拒绝整轮（`channel_upstream_update.go:284-288`）
2. ModelMapping 的 redirect source 豁免（`:270-272`）

没有数量上限、没有连续确认、没有实际验证。

### 最坏情况（已验证可达）

上游换了 API 版本或返回空壳列表（如 `{"data":[{"id":"default"}]}`），`len(upstream)=1` 通过空列表检查，然后本地全部模型被判为 pendingRemove → 一轮删光 → 触发 `:414-420` 的 `AutoDisableChannelById` → **整个渠道被自动禁用**。

### 目标

在自动同步的 diff 结果上加一道**真实请求验证门**：pendingAdd 探测通过才加，pendingRemove 探测确认不存在才删。

### 范围边界（有意为之）

- **只探 diff**（pendingAdd + pendingRemove），不做全量探测、不做轮转扫描
- **不新建任何数据库表**，探测结果只作为本轮 diff 的否决票，不持久化为状态
- 因此**不解决**「上游列表虚报僵尸模型」（两边都有 → diff 为空 → 探针不触发）。该场景留待后续迭代，候选方案：在 relay 链路捕获 `model_not_found` 错误做精准摘除
- 日志复用现有 `logs` 表，前端零改动

### 已拍板的 4 个决策

| # | 决策 | 取值 | 理由 |
|---|---|---|---|
| 1 | 探测预算作用域 | 每渠道 30 + 全局每轮 200 | 只设全局 30 时，渠道多了绝大多数渠道一轮探不到任何模型 |
| 2 | 多 key 渠道遇到 `not_found` | 降级为 `inconclusive`，不删 | 探针只用了一个 key，OpenAI 把「不存在」和「无权限」合并进同一句错误消息，可能误删其他 key 能服务的模型 |
| 3 | 连续 429 中止的作用域 | 单渠道 | A 渠道限流不代表 B 渠道限流 |
| 4 | 比例保护的本地模型数下限 | >= 5 才启用 | 见约束 C |

## 二、方案设计

### 关键约束（均已验证代码，实现时必须遵守）

**A. 不能复用 `testChannel`**

`controller/channel-test.go:294` 有 `strings.Contains(channel.Models, specifiedModel)` 白名单检查。pendingAdd 的模型压根不在 `channel.Models` 里，必然返回 `specified model 'X' is not supported by this channel`。必须新写独立 probe 函数。

> 顺带记录：该处用 `Contains` 做子串匹配本身是 bug（`gpt-4` 会命中 `gpt-4o`）。本次不修，避免动 `testChannel` —— 它挂着管理员测活和自动启停渠道两条命脉。

**B. 裸 404 不能直接判 `not_found`**

base_url 配错或上游反代挂掉时，**所有**模型都返回 404 → 全量误删。404 必须**同时**成功解析出非空 JSON `Error.Message` 才算 `not_found`；404 + 空 body / HTML body → `inconclusive`。

**C. 比例保护会关掉现有的「模型全删 → 自动禁用渠道」链路**

本地只有 1-3 个模型时，任何删除都 ≥50%，会被比例守卫拦掉，`:371 / :388 / :414-420` 的 `allModelsRemoved → AutoDisableChannelById` + `autoReenabled` 逻辑静默失效。必须加本地模型数下限。

**D. 超时必须外层自己包**

`relay/util/init.go` 的 `HTTPClient.Timeout` 默认 **5 分钟**，且 `relay/channel/common.go:36-38` 明确「不绑定客户端 context」。30 模型串行 × 5min = 2.5 小时/渠道，而 `runUpstreamUpdateTaskOnce` 是串行遍历所有渠道的。必须 `goroutine + buffered chan + select` 包一层 wall-clock 超时。

**E. 不能复用 `RecordConsumeLogWithOtherAndRequestID`**

`model/log.go:130` 的 `metrics.ObserveConsume` 故意放在 `if !config.LogConsumeEnabled { return }` **之前**（`:120-129` 注释解释了原因），复用会污染 `oneapi_llm_*` Prometheus 指标；且 `:155` 硬编码 `Type: LogTypeConsume`。必须新写 `RecordModelProbeLog`。

**F. 未知模型倍率是 30**

`common/model-ratio.go:463` `GetModelRatio` 对未知模型 `return 30`。pendingAdd 全是新模型，quota 会按 30 倍算。绝对值仍很小（~5 prompt + ≤16 completion token），但要在日志 `Content` 里注明倍率来源。

### 判定规则：四态

**`skipped`**（探测前判定，不发请求）

`isUnsupportedTestChannel(channel.Type)`（`channel-test.go:89`）、`isUnsupportedTestModel(modelName)`（`:94`）、`isCodexModel(modelName)`（`:108`，第一版不支持 `/v1/responses` 探测）、key 为空 / `GetNextAvailableKey` 报错 / `helper.GetAdaptor` 返回 nil。

**`alive`**

```
err == nil && apiErr == nil && statusCode == 200 && usage != nil
&& (choices 非空 || usage.CompletionTokens > 0 || usage.TotalTokens > 0)
```

不要把「choices 非空」当硬条件 —— AWS/Vertex 等走 SDK 的适配器可能不填 recorder（`testChannel:343` 就专门处理了 `resp == nil`）。

**`not_found`**（三个明确信号之一，大小写不敏感；多 key 渠道按决策 2 降级为 `inconclusive`）

1. `statusCode == 404` **且** 成功解析出非空 `Error.Message`（约束 B）
2. `Error.Code` 或 `Error.Type` ∈ `{model_not_found, invalid_model, model_not_exist, model_not_support, ModelNotFound}`
3. `Error.Message` 命中关键词白名单：`model not found` / `model_not_found` / `does not exist` / `no such model` / `unknown model` / `invalid model` / `unsupported model` / `model is not supported` / `模型不存在` / `不支持该模型` / `未找到模型` / `无此模型`

**`inconclusive`**：其余全部 —— 401/403/429/402/400/5xx、超时、网络错误、JSON 解析失败、内容审核拦截、`usage == nil`、超出探测预算、429 中止后的剩余模型。

> `Error.Code` 是 `any` 类型（可能 string 或 float64），需 `fmt.Sprintf("%v", code)` 归一化。

### 判定规则：处置动作

| 方向 | `alive` | `not_found` | `inconclusive` | `skipped` |
|---|---|---|---|---|
| pendingAdd | **加** | 不加 | 不加 | **加**（信任上游） |
| pendingRemove | 不删 | **删** | 不删 | **删**（信任上游） |

核心原则：

- `inconclusive` 一律「不动」—— 下轮 diff 从零重算会自然重现，等于自动重试
- `skipped` 一律「信任上游」—— 对无法探测的模型完全不改变现有行为，上线不引入回归

**手动 apply 路径不走探针**（`doApplyChannelUpstreamModelUpdates`，`:643`），管理员保留最终决定权 —— 否则渠道持续限流时管理员会被探针锁死。

### 改动清单

#### 1. `controller/channel_upstream_update.go`（修改，4 处）

**改动 1 — 修 `isIgnored` 不拦 pendingRemove（bug 修复）**，`:269-275`

`:262-267` 的 pendingAdd 有 `!isIgnored(m)` 过滤，而 pendingRemove 没有 → `IgnoredModels` 只拦新增不拦删除。实际后果：管理员手动加了一个上游 `/v1/models` 不暴露但实际可用的模型，加进忽略列表以为受保护，结果被 AutoDelete 删掉。给 pendingRemove 补上 `isIgnored` 检查。

**改动 2 — 探针过滤**，插在 `checkAndPersistUpstreamChanges`（`:341`）的 `:362` 之前

```
approvedAdd, approvedRemove := pendingAdd, pendingRemove
if allowAutoApply && 探针开启 && 本渠道未关闭探针 {
    // 只在会真正生效时才探，否则结果只进人工队列，白花钱
    if AutoSyncEnabled && len(pendingAdd) > 0     { 探 → approvedAdd }
    if AutoDeleteEnabled && len(pendingRemove) > 0 { 探 → approvedRemove }
}
```

`:364` 和 `:382` 两段改用 `approvedAdd` / `approvedRemove`。

**settings 回填必须以原始 pending 为基准**：`:375` 的 `LastDetectedModels = []string{}` 改为 `upstreamSubtractModelNames(pendingAdd, approvedAdd)`，`:389` 的 `LastRemovedModels` 同理。这样 `inconclusive` / `not_found` 的模型留在 settings 里，管理员在 UI 上能看到并手动决策。

**改动 3 — 批量删除比例保护**（独立于探针，探针关闭时也生效），`:382` 条件里加守卫

```
if 阈值 > 0 && len(localModels) >= 下限 && len(approvedRemove)*100 > len(localModels)*阈值 {
    → 不自动删，保留 LastRemovedModels 供人工审核 + upstreamError 告警
}
```

这是探针失效时（如限流导致全部 `inconclusive`）的第二层网。

**改动 4 — 每轮预算传递**，`runUpstreamUpdateTaskOnce`（`:472`）

全局每轮预算需跨渠道共享。用包级 `atomic.Int64` + 每轮开头 Store 重置（`upstreamUpdateTaskRunning` 的 `atomic.Bool` CAS 已保证同一时刻只有一轮在跑）。这样 `checkAndPersistUpstreamChanges` **签名完全不变**，三个 HTTP handler 调用点无需改动。

`:538-543` 的收尾日志加探针统计（`probed / alive / not_found / inconclusive`）。

#### 2. `controller/channel_upstream_probe.go`（新增）

纯函数（可单测，无 IO）：`classifyProbeError`、`isModelNotFoundMessage`、`normalizeErrCode`、`filterByProbeVerdicts`、`shouldBlockBulkRemove`。

有 IO：`doProbeChannelModel`、`probeChannelModel`（包超时）、`probeChannelModels`（批量 + 预算控制）。

`doProbeChannelModel` 复制 `channel-test.go:251-352` 的骨架，4 处改动：

1. **去掉** `:294` 的 `channel.Models` 白名单检查（约束 A）
2. **保留** `:326` 的 `util.GetMappedModelName`（与 testChannel 及真实请求路径一致）。

   > 修订记录（2026-08-06）：原计划写的是「去掉映射，pendingAdd 是上游真名、pendingRemove 已排除 redirect source，用原名都正确」。这个论证只回答了「上游有没有这个名字」，而探针真正要回答的是「模型加进本地列表后用户请求能否成功」—— 用户请求走的就是映射后的名字。不套映射会让探针验证的链路与真实调用链路不同，探针报 alive 而用户实际调用失败，比不探更糟。另一层理由：管理员显式配置 model_mapping 表达了「该模型要用映射名调上游」的意图，应优先于 `/v1/models` 的自动发现结果。
3. `MaxTokens = config.UpstreamModelProbeMaxTokens`，`Stream = false`
4. 保留 `resp.StatusCode` 和完整 `*ErrorWithStatusCode`。**不改任何现有签名**

`middleware.SetupContextForSelectedChannel(c, channel, "")` 照抄 `testChannel` 传空 modelName —— `middleware/distributor.go:303` 会因此跳过 `metrics.IncChannelAttempt`，不污染渠道成功率。

`probeChannelModel` 的超时包装（约束 D）：`done := make(chan probeResult, 1)`（**必须带 buffer**，否则超时后 goroutine 永久泄漏）+ `select`。泄漏的 goroutine 上限 = 探测预算，且会在 HTTPClient 超时后自行退出。

## 三、影响范围

- **探针关闭时（默认）**：仅改动 1（`isIgnored` 拦删除）和改动 2（比例保护）生效，二者都是收紧删除条件 → 只会更保守，不会多删
- **不影响**：手动 apply 路径、`testChannel` / 渠道测活、relay 主链路、abilities 表结构、`oneapi_llm_*` 指标、营收统计
- **无数据库迁移**：不新建表；`channel_other_settings.go` 新字段用 `omitempty` + 负极性，现有 settings JSON 零变化
- **前端零改动**

### 行为变更（需在 CHANGELOG 写明）

1. `IgnoredModels` 现在**同时拦截自动删除**。用宽 regex 规则（如 `regex:.*`）的用户会感知 —— 这些模型从此永不被自动删除
2. 探针产生真实上游请求与真实 token 成本，`UpstreamModelProbeEnabled` 默认关闭

### 已知遗留（本次不做）

1. **僵尸模型**（上游列表虚报、diff 为空）探不到 —— 见范围边界
2. **`not_found` 的 pendingAdd 每轮重探**：上游一直虚报就一直烧钱。可选缓解（不违反「不建表」）：进程内 `sync.Map` 缓存 `channelID:model → not_found`，TTL 24h，重启失效。先观察真实成本再决定
3. **`channel-test.go:294` 的 `Contains` 子串匹配 bug**（`gpt-4` 命中 `gpt-4o`）—— 单独立项修
4. **Codex 模型不探**（判 `skipped`）：`testChannelViaResponses`（`:115`）内部会调 `recordChannelTestConsumeLog` 写 `LogTypeConsume` 污染日志
5. **`DeleteDisabledChannel`（`model/channel.go:830-838`）只删 channels 不删 abilities**，留下孤儿 ability 行 —— 探索时顺带发现的现存 bug，单独立项修

## 四、验证方式

### 单元测试

```bash
go build ./... && go vet ./...
go test ./controller/... -run 'TestClassifyProbeError|TestFilterByProbeVerdicts|TestUpstreamCollect|TestShouldBlockBulkRemove' -v
```

改动 1 的回归测试要在改代码前先跑一次确认 FAIL，改完再 PASS。

`controller/` 包此前**没有任何测试文件**，`upstreamCollectPendingChangesFromModels` 零覆盖。新增两个测试文件，全部纯函数、不需要 DB。风格是 stdlib `testing` + 手写表驱动（参考 `relay/util/stream_status_test.go`）。

必须包含的回归/防误判 case：

| case | 期望 | 守的是什么 |
|---|---|---|
| 404 + 可解析错误体 | `not_found` | 正常路径 |
| 404 + 空 body | `inconclusive` | 约束 B |
| 404 + HTML body | `inconclusive` | 约束 B |
| `Code: float64(404)` | `inconclusive` | `any` 类型归一化 |
| `Message: "该模型不存在"` | `not_found` | 中文关键词 |
| 403 + `"You do not have access to this model"` | `inconclusive` | 白名单边界：`do not have access` 不能命中 |
| 400 + `"This model's maximum context length is 4096"` | `inconclusive` | 白名单边界：不能被 `model` 类词误命中 |
| 多 key 渠道 + 404 + 可解析体 | `inconclusive` | 决策 2 |
| `isIgnored` 拦 pendingRemove | 不在 pendingRemove 里 | 改动 1，改动前必须 FAIL |
| 本地模型 < 下限时不拦删除 | 放行 | 约束 C |

### 灰度上线

1. `UpstreamModelProbeEnabled=false` 上线，确认巡检行为与之前完全一致
2. 挑一个模型数多、上游不太稳的渠道，只对它开探针，观察一轮
3. 前端日志页筛 `类型=系统` + `令牌名称=model-probe`，逐条核对：
   - verdict 分布（`inconclusive` 占比过高 → 分类规则太严或上游在限流）
   - 单次探测耗时（接近 20s 超时 → 需调 `UpstreamModelProbeTimeoutSeconds`）
   - 有没有 `not_found` 判错的（拿日志里的状态码 + 错误手动 curl 复现）
4. 观察 `oneapi_llm_*` Prometheus 指标**没有**因探针出现毛刺（验证约束 E）
5. 确认 `models` 字段变更符合处置表；`inconclusive` 的模型确实留在 UI 待处理队列
6. 分布无异常后再放开全量

### 手动验证约束

- **约束 A**：给某渠道构造一个上游有、本地没有的模型，确认探针能探到（不再报 `not supported by this channel`）
- **约束 B**：把某渠道 base_url 改成返回 404 HTML 的地址，确认所有模型判 `inconclusive` 而非被全量删除
- **约束 C**：找一个只有 2-3 个模型的渠道，确认上游删空时「自动禁用渠道」链路仍然工作
- **约束 D**：对比开启前后的巡检收尾日志时间戳，确认单轮巡检总耗时没有爆炸
