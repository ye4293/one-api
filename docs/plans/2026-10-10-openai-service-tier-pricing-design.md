## 0. 官网核验结果（2026-10-11）

本轮已读取 OpenAI 官方模型页面、API 参考、档位指南及价格表。以下名称和价格以本次访问结果为准，配置价格仍由现有系统维护，不新增官网抓价或自动同步功能。

### 0.1 模型 ID 与档位字段

官网已确认的模型 ID 为 `gpt-6-astra`、`gpt-6.1-sol`、`gpt-6-sol`、`gpt-6-luna`。它们分别出现在[模型目录](https://developers.openai.com/api/docs/models)或[官方价格表](https://developers.openai.com/api/docs/pricing)中；不能将其省略成 `gpt6`，也不编造尚未核实的日期快照名称。

| 官网展示名称 | 请求参数与响应依据 | 本系统最终取价键 |
|---|---|---|
| Standard | `default` 表示标准价格和性能 | 原模型名，不读 `_default` |
| Flex | 请求使用 `flex`；实际响应为 `flex` 时按该档位结算 | `模型_flex` |
| Fast（原 Priority） | 请求接受 `fast` 或 `priority`；API 参考说明响应返回 `priority`，Fast 指南明确 GPT-5.6 及以前返回 `priority` | 响应 `priority` 查 `模型_priority`；若实际上游返回 `fast`，查 `模型_fast` |
| Ultrafast | 请求使用 `ultrafast`；实际响应为 `ultrafast` 时按该档位结算 | `模型_ultrafast` |

依据：[Responses 创建接口的 `service_tier` 说明](https://developers.openai.com/api/reference/resources/responses/methods/create)、[Fast mode](https://developers.openai.com/api/docs/guides/fast-mode)、[Flex processing](https://developers.openai.com/api/docs/guides/flex-processing)、[Ultrafast mode](https://developers.openai.com/api/docs/guides/ultrafast-mode)。官方说明响应档位可能与请求不同；Fast 降级时会返回 `default` 并按 Standard 收费。这直接支持本设计“以响应为准”的选择方式。

`auto` 表示按项目设置选择处理方式，项目未另行配置时使用 `default`；省略请求字段也采用 `auto` 行为。因此不能用请求的 `auto` 或缺省状态提前推断最终档位，更不能补写到响应日志中。

官方不同页面目前存在说明范围差异：API 参考仍将 Ultrafast 的可用模型描述为 `gpt-5.6-sol`，Ultrafast 指南已写明 GPT-6 Astra，而价格表和 [GPT-6.1 Sol 模型页](https://developers.openai.com/api/docs/models/gpt-6.1-sol)还列出该模型的 Ultrafast。Fast 响应名称的说明范围也有上述差异。因此本设计不固化“全部模型都支持四档”或“全部 Fast 响应固定使用同一名字”的假设；按实际响应原值取价，模型及档位可用性以对应模型文档和实际接口为准。本次不增加 WebSocket 接入或新的档位校验流程。

### 0.2 长上下文阈值与各档位价格

[GPT-6 Astra](https://developers.openai.com/api/docs/models/gpt-6-astra)、[GPT-6.1 Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol)、[GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna)的模型页明确写明：总输入超过 `272K` token 后，**整次请求**按输入及缓存价格 ×2、输出价格 ×1.5 计算。恰好 `272000` 不触发；不是只对超出部分加价。价格表中 `gpt-6-sol` 的短/长上下文价格也符合相同系数。

以官方价格表的 `gpt-6-astra` 为例，单位均为美元/百万 token，元组顺序为“输入 / 缓存读 / 缓存写 / 输出”：

| 档位 | 短上下文单价（总输入 ≤272000） | 长上下文单价（总输入 >272000） |
|---|---|---|
| Standard | `10 / 1 / 12.5 / 50` | `20 / 2 / 25 / 75` |
| Fast | `20 / 2 / 25 / 100` | `40 / 4 / 50 / 150` |
| Flex | `5 / 0.5 / 6.25 / 25` | `10 / 1 / 12.5 / 37.5` |
| Ultrafast | `60 / 6 / 75 / 300` | `120 / 12 / 150 / 450` |

来源：[Standard](https://developers.openai.com/api/docs/pricing)、[Fast](https://developers.openai.com/api/docs/pricing?latest-pricing=fast)、[Flex](https://developers.openai.com/api/docs/pricing?latest-pricing=flex)、[Ultrafast](https://developers.openai.com/api/docs/pricing?latest-pricing=ultrafast)价格表。本轮逐档查看了页面显示的短/长上下文价格。

这验证了“先取具体档位的短上下文单价，再乘现有长上下文系数”的方案。配置中应保存短上下文价格，不能先保存长上下文价格后再乘一次系数，也不应把某个模型的 Fast/Ultrafast 相对 Standard 的价格倍数硬编码成所有模型的档位公式。

上述是官网价格快照，不会自动写入运行配置，也不代表当前代码已支持这些模型的长上下文阈值。本次设计保留第 2.4 节的 GPT-6+ 阈值扩展；未来主版本的默认覆盖是平台策略，不是官方对未来模型定价的承诺。

## 1. 最终采用的规则

上游响应返回非空且不为 `default` 的 `service_tier` 时，用当前计费模型名拼接下划线和响应值，在现有价格配置中查找：

```text
pricing_key = model_name + "_" + response.service_tier
```

例如模型 `gpt-6-astra` 返回 `priority`，优先读取 `gpt-6-astra_priority` 的配置。

1. 拼接键的某项价格已配置：该项使用拼接键的值。
2. 拼接键的某项价格未配置：该项回退原模型原有值。
3. 响应未返回档位，或者字段为 null / 空字符串 / `default`：所有价格沿用原模型；即使存在 `模型_default` 配置也不读取。
4. 只依据响应实际值，不根据请求档位选择最终价格，也不补一个默认 Standard。
5. 取出的价格代入原有公式，保留原有折扣、取整和扣费流程。
6. 长上下文也必须以实际响应档位的单价为基础计算：先取 `模型_档位` 的输入、输出及缓存价格，再带入原长上下文公式；不能在长上下文分支重新取原模型单价。`default`、无档位及未配置项按上述规则回退。
7. 只有 OpenAI 响应计费链路采集到非默认档位，且该入口至少命中一项可用的档位价格配置时，才覆盖原价格；其余情况使用原模型价格。
8. 长上下文独立按基础计费模型判断：保留已有阈值，增加 GPT-6 及后续主版本的默认 `272000` 阈值。总输入严格超过阈值时，已选单价的输入/缓存 ×2、输出 ×1.5；`default`、缺失档位及配置未命中时也适用，以原模型单价计算。

普通请求和长上下文请求使用同一个价格选择入口，差别仅是后续是否应用现有长上下文系数：

| 响应 `service_tier` | 普通上下文的价格来源 | 长上下文的价格来源与计算 |
|---|---|---|
| `priority`，对应项有配置 | `模型_priority` 的对应价格 | 同一组 priority 单价进入原长上下文公式 |
| `fast`，对应项有配置 | `模型_fast` 的对应价格 | 同一组 fast 单价进入原长上下文公式 |
| `flex`，对应项有配置 | `模型_flex` 的对应价格 | 同一组 flex 单价进入原长上下文公式 |
| `ultrafast`，对应项有配置 | `模型_ultrafast` 的对应价格 | 同一组 ultrafast 单价进入原长上下文公式 |
| 非默认档位，但某项未配置 | 该项回退原模型参数 | 该项回退原模型参数后进入原长上下文公式 |
| `default` | 原模型价格，忽略 `_default` 配置 | 原模型价格进入原长上下文公式 |
| 未返回、null 或空字符串 | 原模型价格 | 原模型价格进入原长上下文公式 |

这里的“具体档位单价”指现有价格表中 `模型_档位` 对应的价格。不新增 `模型_档位_long` 键，不用独立长上下文价格表替换原计算流程。`default` 只影响价格选择，不关闭原模型的长上下文计费。

本版替代此前较重的设计：不增加独立档位配置、价格版本、完整性门槛、配置事务、渠道名称检查或新的管理接口；不调整预估、预扣、重试和流式生命周期。

### 1.1 兼容性约束

本次允许两项行为变化：**命中的档位价格用于结算，以及 GPT-6+ 按基础模型启用长上下文规则。** 两者相互独立。未命中档位配置时价格回退原模型，但 GPT-6+ 超过长上下文阈值的 token 请求仍会因新增系数改变费用；这是明确要求的变化，不能承诺该场景与旧费用一致。其他场景按相同配置、相同用量与原实现比较，扣费及日志行为必须保持一致。

| 场景 | 本次必须保持的行为 |
|---|---|
| 没有返回档位、null、空字符串、`default` | 不读取档位价格，忽略 `_default`；长上下文按基础模型判断，包括新增的 GPT-6+ 规则 |
| 返回非默认档位，但没有命中该入口使用的档位配置 | 使用原模型价格；除 GPT-6+ 长上下文扩展外，原额度与流程不变 |
| 命中部分档位配置 | 仅覆盖命中的价格参数；其余参数及原公式不变 |
| 已有长上下文模型 | 基础模型、阈值、输入统计和系数不变，命中时仅替换参与计算的单价 |
| GPT-6 及后续主版本 | 显式阈值优先，否则使用 `272000`；总输入超过阈值后为 `2 / 1.5` |
| 其他未注册长上下文的模型 | 继续返回 `1 / 1`，不扩大识别范围 |
| 非 OpenAI 响应计费链路 | 不新增取价入口，不改变 Claude、Gemini、图片、音频等独立计费行为 |

共用长上下文函数的现有调用方，若基础计费模型为 GPT-6+，会获得新增阈值；这属于本次预期范围。该函数不读取响应档位，也不修改模型映射。按次计费继续优先走原分支，不因输入超过阈值而给整笔固定价格乘系数。

请求透传、响应采集、模型映射、路由、预估预扣、余额检查、用户/渠道折扣、按次计费优先级、取整、最低额度、零 token、异常用量处理、流式/重试生命周期及账单发送保持原规则。最低额度分支仅在档位输入倍率命中时使用该次实际倍率，见第 4.1 节；不重新定义原条件。

价格 getter 和导出计算函数的签名保持不变；共用 `GetLongContextMultipliers()` 仅扩展第 2.4 节的模型范围，其原有系数、已有精确阈值及调用口径不变。不新增管理接口、日志字段或数据库结构，也不自动填充、覆盖现有基础模型价格。

## 2. 价格如何查找

### 2.1 按配置项分别回退

| 配置项 | 优先精确查找 | 未命中时 |
|---|---|---|
| `ModelRatio` | `ModelRatio[模型_响应档位]` | 使用调用方原有输入倍率 |
| `CompletionRatio` | `CompletionRatio[模型_响应档位]` | `GetCompletionRatio(原模型)` |
| `CacheRatio` | `CacheRatio[模型_响应档位]` | `GetCacheRatio(原模型)` |
| `CacheWriteRatio` | `CacheWriteRatio[模型_响应档位]` | `GetCacheWriteRatio(原模型)` |
| `ModelPrice`，对应 `PerCallPricing` | `ModelPrice[模型_响应档位]` | `GetModelPrice(原模型, false)` |

上表查出的档位价格同时用于普通和长上下文计算。价格在现有代码中以输入倍率及输出/缓存相对倍率表达，沿用这种存储方式，不另建一套档位长上下文倍率表。

原有 getter 会对未知模型使用默认值，因此不能先调用 `GetModelRatio("模型_priority")` 再猜测是否命中；应通过 map 的 `value, exists` 判断拼接键是否有显式配置。

判断的是键是否存在，不能用 `value != 0` 判断。显式配置 0 仍使用 0，负数或其他特殊值沿用当前配置与计费流程的既有含义，不在本次新增校验。

不要求几项同时配置。只配置输入倍率时，输出及缓存沿用原模型的**相对倍率**，相应单价会随新的输入倍率变化；如需独立控制实际输出/缓存单价，应一起配置对应倍率。

### 2.2 档位值和模型名

- `default` 是明确的原模型计费分支，不拼接后缀；除此之外直接使用上游响应值，不转换大小写，不设置四档白名单。
- 官方展示名 Standard 对应 `default`；Flex 对应 `flex`；Ultrafast 对应 `ultrafast`。不能将展示名直接作为响应字段值。
- Fast 请求支持 `fast` 和 `priority`，结算仍只依据响应。返回 `priority` 查 `_priority`，返回 `fast` 查 `_fast`；本次不增加这两个值之间的别名回退。若接入渠道可能返回两种值，可在现有配置中分别配置相同价格。
- `Fast`、`fast`、`priority` 是不同键。兼容上游若实际返回非官方写法 `Fast` 或 `Standard`，仍原样查 `_Fast` 或 `_Standard`；不将其当成官方枚举，也不擅自改写为其他值。
- 不把无档位或 `default` 映射为 `_standard` / `_Standard`；这些配置都不是官方 Standard 分支的价格来源。
- `auto` 是请求侧的选择策略，不据此推断结算档位。若兼容上游在响应中返回 `auto`，仍按非空、非 `default` 值查 `_auto`，未配置则回退；日志保留原值。
- 模型本身含下划线时原样拼接，不反向拆分模型名。
- 不修改客户端请求的 `model`、模型映射结果、上游模型名、渠道路由或日志主体模型名。
- `gpt-6-astra_priority` 等拼接名称只作为本系统内部价格键，**不是 OpenAI 官方 model ID**，也不发给上游。
- 沿用原价格表的全局模型名范围；同名模型在不同渠道的独立定价不在本次范围内。
- 配置档位键时应避免与已有真实模型名重名；本次不新增自动冲突检测或保留名称机制。

### 2.3 长上下文使用具体档位的单价计算

先按响应档位选择价格，再判断是否进入长上下文计算。无论输入是否超过长上下文阈值，价格来源都遵循同一套响应档位规则。

例如基础模型为 `gpt-6-astra`，响应返回 `priority`：单价查 `gpt-6-astra_priority`，阈值及系数按 `gpt-6-astra` 取得。总输入 `272001` 时，已选输入/缓存单价 ×2、输出单价 ×1.5；响应改为 `default` 时，改用 `gpt-6-astra` 的单价再乘同样系数。无需配置 `gpt-6-astra_priority` 的独立长上下文倍率。

当前 `LongContextThreshold` 记录基础模型的触发阈值，`GetLongContextMultipliers()` 在超过阈值后返回输入/缓存系数 `2`、输出系数 `1.5`。本版保留已有模型阈值和计算系数，并在该函数中增加第 2.4 节的 GPT-6+ 默认阈值。取价使用档位键，阈值判断使用基础模型键；不能把两种用途合并成一个模型名后传遍所有函数。

计算步骤：

1. 响应非空且不为 `default` 时，按第 2.1 节选取档位价格及未配置项的回退值；否则使用原模型价格。
2. 按基础计费模型调用 `GetLongContextMultipliers()`：优先现有 `LongContextThreshold` 精确配置，其次应用 GPT-6+ 的默认阈值；继续使用 `总输入 token > 阈值`，恰好等于阈值不触发。
3. 基础模型没有阈值或未超过阈值时，长上下文输入/缓存、输出系数均为 `1`，直接用已选出的单价计算。
4. 已触发时，已选出的输入、缓存读、缓存写单价乘原长上下文输入系数，输出单价乘原长上下文输出系数，各项只乘一次。
5. 长上下文分支不能重新查询基础模型的 `ModelRatio`、`CompletionRatio` 或缓存价格覆盖已经选出的档位价格。
6. 响应为 `default` 时，无论是否配置了 `模型_default`，普通单价和用于长上下文计算的单价都取原模型；请求中的 priority/flex 等值不参与此次选择。

按当前单价换算口径，可表达为：

```text
M、R、CR、CW = 本次依据响应档位选出的输入/输出/缓存读/缓存写倍率
LI、LO       = 原长上下文规则按基础模型及本次总输入算出的系数

长上下文输入单价   = 2 × M × LI
长上下文输出单价   = 2 × M × R × LO
长上下文缓存读单价 = 2 × M × CR × LI
长上下文缓存写单价 = 2 × M × CW × LI
单位：美元/百万 token
```

这里的 `2` 是现有 `ModelRatio` 到单价的换算常数，与长上下文输入系数 `LI` 分开。此前草稿拟新增的 `LongContextInputRatio` / `LongContextOutputRatio` 两张表不纳入本版；本版落实的是“用具体档位单价进入原长上下文计算流程”。

### 2.4 GPT-6 及后续版本的长上下文覆盖

2026-10-11 已访问官方模型详情和价格表，确认 `gpt-6-astra`、`gpt-6.1-sol`、`gpt-6-sol`、`gpt-6-luna` 这些 API 模型 ID；模型名中的连字符、小版本中的小数点都必须保留。第 0 节列出来源及已核实的长上下文计价规则。

在当前已核实模型之外，按主版本号大于等于 `6` 自动覆盖后续模型，是需求方指定的平台默认策略，包含 GPT-6 本身。它不是 OpenAI 对未来模型名称、可用档位或定价的承诺；GPT-7 / GPT-10 等仅作版本解析测试数据，不作为已发布模型写入配置。未来若官方阈值不同，可用精确阈值覆盖；若输入/输出系数不同，则需另行调整现有计算逻辑，单改阈值无法改变系数。

阈值选择顺序：

```text
基础计费模型在 LongContextThreshold 中有精确配置：使用显式阈值
否则，符合 gpt-<版本> 命名且主版本号 >= 6：阈值为 272000
否则：没有长上下文规则，保持输入/输出系数 1
```

模型识别使用基础计费模型名，不包含本功能拼接的 `_priority`、`_fast`、`_flex`、`_ultrafast` 等档位后缀。拟按小写 `gpt-` 前缀解析主版本整数，允许小版本和以 `-` 分隔的模型变体/日期后缀，例如可使用 `^gpt-([1-9][0-9]*)(?:\.[0-9]+)?(?:$|-)` 提取主版本，再判断其数值是否大于等于 `6`。这是一条平台匹配规则，能覆盖本次核实的 ID，不是官网发布的命名规范。不能用字符串大小比较，也不能只匹配 `gpt-6` 前缀而漏掉后续主版本。实际 model ID 不符合此模式时，应补充精确配置，不猜测或改写上游名称。

| 基础模型或模式 | 本设计中的处理 |
|---|---|
| `gpt-6-astra`、`gpt-6.1-sol`、`gpt-6-sol`、`gpt-6-luna` | 官网已核实的 ID；未显式配置时使用 `272000` |
| 未来符合上述模式、主版本 ≥6 的实际 model ID | 按平台策略使用 `272000`；上线新模型时核对其官方定价 |
| `gpt-5.4`、`gpt-5.4-2026-03-05`、`gpt-5.4-pro`、`gpt-5.4-pro-2026-03-05`、`gpt-5.5`、`gpt-5.5-pro`、`gpt-5.6-sol`、`gpt-5.6-terra`、`gpt-5.6-luna` | 当前仓库已有的 9 项，继续使用显式阈值 `272000`；此列表说明仓库现状，不是本轮对所有旧快照名称的官方核验 |
| 未注册且主版本低于 6 的名称 | 不因新增规则自动启用 |
| `my-gpt-6`、`gpt6`、其他供应商名称 | 不猜测别名含义，沿用现有显式配置及模型映射机制 |

输入统计仍使用现有总输入 token，包含已有 usage 中计入总输入的缓存部分；不以扣除缓存后的普通输入判断阈值，也不加上输出 token。

- 总输入 `271999` 或 `272000`：输入/缓存与输出系数均为 `1`。
- 总输入 `272001` 及以上：输入/缓存系数为 `2`，输出系数为 `1.5`。
- 超过阈值后，对该次请求全部相应 token 应用系数，沿用原流程；不是只对超过 `272000` 的部分加价。
- 响应为 priority/flex 等档位时，这些系数作用于该档位命中的价格；响应为 default 或缺失时，作用于原模型价格。

该扩展已在工作区的 `GetLongContextMultipliers()` 中实施并通过本地验证，不表示运行中的服务已经发布支持。现有调用该函数的结算入口和日志文案共同获得新阈值范围，不各自维护 GPT 版本识别规则。Chat 与 Responses 仍按各自原有基础计费模型选择方式调用；自定义别名未解析成标准名称时，不额外读取响应模型或改动模型映射口径。

## 3. 代码组织

拟新增 `relay/controller/openai_pricing.go`，只提供精确查找档位覆盖项的小函数（以下为设计伪代码）：

```text
lookupOpenAIPriceOverrides(基础计费模型, 响应service_tier, 当前结算入口)
    响应档位为空或等于"default"：返回无覆盖
    构造 基础计费模型_响应档位
    仅查当前入口实际使用的价格 map，逐项保留 value 和 exists
    没有命中项：返回无覆盖
    有命中项：返回覆盖值及各项是否命中的标记

结算调用方
    无覆盖：执行原有取价、计算和日志路径
    有覆盖：在原取价点仅替换命中项，未命中项仍按原位置和规则读取
    无论是否命中档位，长上下文都按基础模型调用共用函数
    函数优先使用显式阈值，其次使用 GPT-6+ 默认阈值 272000
    将选定价格代入原公式；该分支记录同一次计算使用的参数
```

标记用于区分“未配置”和“显式配置 0”，不新增配置存储、请求级价格版本快照或全局配置锁。返回对象不带新的长上下文识别规则，也不改动共享请求/响应结构体。

原有价格 getter、`LongContextThreshold` 中的已有项目、options 存储及同步保持不变。仅在 `GetLongContextMultipliers()` 增加基础模型为 GPT-6+ 时的默认阈值判断，保持函数签名及原有系数不变。`CacheWriteRatio` 虽有 map，但目前未接入价格管理接口；本次只读取 map 中已有的档位项，未命中沿用原模型倍率，不补齐管理功能。

Chat 可读取已有按次价格配置 `ModelPrice`；Responses 只读取其原流程使用的 token 价格项。如果只配置了 Responses 原本不用的按次价格，则对该入口视为没有覆盖，不引入按次计费能力。

## 4. 接入现有结算流程

### 4.1 Chat / Completions

在 `relay/controller/helper.go` 的 `postConsumeQuota` 取价处：

1. 使用原来的 `meta.BillingModelName()`，为空时继续回退 `textRequest.Model`。
2. 从 `openai.ResponseServiceTierContextKey` 读取上游响应档位。
3. 查询档位覆盖项；没有命中时走原路径。命中时仅覆盖对应局部价格变量，输入倍率的回退值仍是请求前传入的 `modelRatio`，不重新查询替换该回退值。
4. 将选出的输入、输出、缓存读、缓存写、按次价格带入原有分支；长上下文系数按基础模型取得，作用于这些已选出的价格，不能在长上下文分支重新取原模型单价。
5. 保留原 `ratio != 0 && quota <= 0` 最低扣费条件，以及其后的零 token 处理顺序。仅当档位输入倍率命中时，将该新增场景使用的局部组合倍率同步为选定输入倍率 × 原组合折扣；无命中时必须继续使用原传入的 `ratio`，不顺带修正旧行为。
6. 按原流程用 `quota - preConsumedQuota` 完成差额结算。

请求阶段继续按原模型预估和预扣，不使用请求 `service_tier`。当前预估不代表最高档位的费用上限；不在本次增加资金冻结或修改余额检查策略。

Chat 原有按次价格优先级不变：拼接键按次价格有配置时使用它，否则回退原按次价格；如果原模型本来按次计费，仅增加档位 token 倍率不会自动将它改为 token 计费。

### 4.2 Responses

在 `relay/controller/opeai_response.go` 处理完上游响应、计算 actual quota 前：

1. 仍使用当前入口的 `original_model` 作为基础计费模型。
2. 获取响应档位并查询该入口使用的档位 token 价格覆盖项；未命中时继续调用原 `CalculateResponseQuotaFromUsageMetadata()`，保留原计费和异步日志调用路径。
3. 命中时，在原计算逻辑取价的位置应用覆盖项，传入拟提取的内部计算函数。保留原 token 提取、异常缓存用量处理、浮点运算顺序、额度换算及整数截断，不重写成另一套“等价”公式。
4. 仅为命中档位的分支，将本次实际参与计算的价格传递给异步日志，沿用现有日志字段和写入条件；该分支不重新查价覆盖已选参数。无命中分支不借此次功能调整原日志查询时机。

`CalculateOpenaiResponseQuotaByRatio()`、`CalculateResponseQuotaFromUsageMetadata()` 等原公开函数保持签名、基础模型价格来源和公式，通过共用长上下文函数获得 GPT-6+ 新阈值。不涉及新增长上下文规则时，结果须与原实现一致；GPT-6+ 超阈值时则验证预期系数。内部函数若需提取，只做必要的参数传递，不另写计算规则。Responses 继续按原 token 公式结算，不增加按次分支；原有余额检查、全额扣费与异步执行方式不变。

### 4.3 流式、其他模型与模型映射

- 普通与流式请求都读取已经采集的响应档位，不重复解析响应或调整 SSE 流程。
- 继续使用现有“最近一个非空档位”记录逻辑，缺失字段不会从请求补值。`default` 是非空的有效响应值：流中先 priority 后 default，应以 default 结算原模型价格，不能保留早先的 priority。
- 沿用既有重试清理逻辑，不额外扩大重试或修复流式中断时序。
- 复用 OpenAI 响应处理器和通用结算的兼容渠道，只有当前响应已采集到档位且命中对应价格时才进入新增分支。不按模型名前缀决定是否启用档位功能，不为其他独立计费入口接入该函数，也不新增对其他响应格式的档位采集。
- Chat 的计费模型通常为映射后名称，Responses 当前为原始名称，保留此差异。
- 长上下文阈值及现有系数按基础模型判断，参与计算的单价按响应档位选择；不能只对旧 `GetLongContextMultipliers` 传入拼接键代替这两个步骤。

## 5. 公式与可复算示例

正常用量下仍按既有公式计算：

```text
普通输入 = 总输入 - 缓存读取 - 缓存写入

金额对应额度 = (
    普通输入 × 输入倍率 × 长上下文输入倍率
  + 缓存读取 × 输入倍率 × 缓存读取倍率 × 长上下文输入倍率
  + 缓存写入 × 输入倍率 × 缓存写入倍率 × 长上下文输入倍率
  + 输出 × 输入倍率 × 输出倍率 × 长上下文输出倍率
) × 原组合折扣
```

Chat 保留向上取整，Responses 保留原额度换算和整数截断；异常用量、零 token、最低额度、固定价格优先级均按各入口原流程处理。

以下为测试数据，非官方价格。设总输入 1000、缓存读 200、缓存写 100、输出 100，长上下文倍率和折扣均为 1：

| 配置/响应情况 | 输入/输出/缓存读/缓存写倍率 | Chat quota | Responses quota |
|---|---|---:|---:|
| 原模型 | `1 / 3 / 0.1 / 1.25` | 1145 | 1145 |
| 返回 priority，完整配置 | `2 / 4 / 0.2 / 1.5` | 2580 | 2580 |
| 请求 priority，实际返回 flex | `0.5 / 2 / 0.1 / 1.25` | 523 | 522 |
| 请求 priority，响应没有档位 | 原模型参数 | 1145 | 1145 |
| 请求 priority，响应 default（即使配置了 `_default`） | 原模型参数 | 1145 | 1145 |
| 返回未配置档位 | 原模型参数 | 1145 | 1145 |
| 返回自定义档位 partial，仅配置输入倍率 2 | `2 / 3 / 0.1 / 1.25` | 2290 | 2290 |

额度单位使用当前默认 `QuotaPerUnit = 500000`。最终结算数不表示请求开始时预扣了相同金额。

补充长上下文验算：仍使用 priority 的价格配置 `2 / 4 / 0.2 / 1.5` 和上述 token 数量，假设测试模型阈值为 `999`，因此输入 `1000` 已触发。保留当前长上下文系数：输入/缓存 `2`、输出 `1.5`。这些价格和测试阈值均为人工测试数据。

```text
输入及缓存原额度 = 700×2 + 200×2×0.2 + 100×2×1.5 = 1780
输出原额度       = 100×2×4 = 800
最终额度         = 1780×2 + 800×1.5 = 4760
```

priority 在此配置下的长上下文输入单价为 `8` 美元/百万 token，输出单价为 `24`，缓存读单价为 `1.6`，缓存写单价为 `12`。这些单价来自 priority 的价格配置与原长上下文系数，并非原模型价格。

相同长上下文用量下，响应 `flex` 时应使用 flex 的价格，最终额度为 `422.5×2 + 100×1.5 = 995`；响应 `default`、无档位或档位完全未配置时使用原模型价格，最终额度为 `845×2 + 300×1.5 = 2140`。`default` 只决定使用原模型单价，不会关闭原模型的长上下文计费。

## 6. 配置示例与日志

继续通过现有价格管理功能配置 `gpt-6-astra_priority` 等价格键，不需要把这些名字加入渠道模型列表。下面按第 0 节官方 Astra 短上下文价格换算，展示现有 options 的逻辑内容，不是新的配置项或新的接口结构。其中同时列出 `_priority` 和 `_fast`，用于兼容实际返回这两种值的上游；这不意味着实现会在两个键之间自动回退。基础模型项仅用于解释价格关系，本次实施不得自动覆盖用户已有价格；档位配置按现有机制增量维护，不用下列片段整体替换完整配置。

```json
{
  "ModelRatio": {
    "gpt-6-astra": 5,
    "gpt-6-astra_priority": 10,
    "gpt-6-astra_fast": 10,
    "gpt-6-astra_flex": 2.5,
    "gpt-6-astra_ultrafast": 30
  },
  "CompletionRatio": {
    "gpt-6-astra": 5,
    "gpt-6-astra_priority": 5,
    "gpt-6-astra_fast": 5,
    "gpt-6-astra_flex": 5,
    "gpt-6-astra_ultrafast": 5
  },
  "CacheRatio": {
    "gpt-6-astra": 0.1,
    "gpt-6-astra_priority": 0.1,
    "gpt-6-astra_fast": 0.1,
    "gpt-6-astra_flex": 0.1,
    "gpt-6-astra_ultrafast": 0.1
  }
}
```

换算方式为 `ModelRatio = 输入单价 / 2`、`CompletionRatio = 输出单价 / 输入单价`、`CacheRatio = 缓存读单价 / 输入单价`。这组配置能复现第 0 节的输入、输出及缓存读价格。缓存写入应使用相对输入倍率 `1.25`；上述 JSON 未新增缓存写入配置入口，只有原模型 `GetCacheWriteRatio()` 实际返回 `1.25` 时，回退才能同时复现表中的缓存写入价格。该值应在实施与配置核对时检查，不能将例子理解成已经补齐管理界面或运行配置。

删除某一档位配置项后，该项恢复使用原模型值；删除所有对应项后整笔恢复原模型价格，不将价格 0 当作删除。长上下文复用同一份档位短上下文价格配置，再应用基础模型的长上下文规则，不需要新增长上下文档位配置表。GPT-6+ 阈值扩展纳入第 2.4 节；实施后使用同一份档位价格乘基础模型长上下文系数。`gpt-6-astra_default` 即使存在，也不会因响应 `default` 而被选中。

日志规则：

- `usageDetails.service_tier` 仍只记录实际返回值，没有返回就不出现；返回 `default` 时原样记录 `"service_tier":"default"`，不能因为按原模型计费就省略该事实。
- 仅命中档位覆盖的分支，将 `billingDetails` 现有输入、输出、缓存及按次价格字段填为本次实际参数；字段名称、类型和出现条件保持原样，未命中分支保留原日志行为。
- 沿用现有日志文案中的 long 输入/输出系数；不新增 `long_input_multiplier` / `long_output_multiplier` 字段。实际价格参数与原文案中的系数组合用于复算，字段解析和日志消费者无须因本次兼容修改结构。
- 不新增 `pricing_version`、复杂回退原因或新的日志表字段。
- `tier_ratio` 仍表示用户等级折扣，不用于服务档位。
- `logs.model_name` 和 shipper 路由模型名不拼接后缀。
- 下游若重算金额，应使用日志里的实际价格参数，不能只按原模型重新查当前价格。

价格管理、内存 map、后台同步和热更新时机仍沿用现有机制，不保证一次请求的所有配置被同一个版本锁定。仅在命中档位的新增分支中，将已选出的倍率同时用于该次计算和消费日志；未命中分支保持原查询时机，不扩展为全局配置并发治理。

## 7. 验证范围

以下为后续实施的验收计划，不代表当前已有实现或已验证通过：

1. 响应档位命中、没有返回、null、空值、default、未配置与大小写不匹配。
2. 请求 priority、响应 flex 时以响应为准；请求有档位但响应没有或为 default 时取原模型，配置了 `_default` 也不使用。
3. 部分配置逐项回退；零值有效；新档位名无需白名单。
4. Chat、Completions、Responses 的普通/流式响应采集到实际扣费、日志的链路。
5. 输入、输出、缓存读写金额及原有取整差异。
6. 按次价格覆盖和回退、零价不被误当成缺失。
7. 长上下文阈值继续按基础模型匹配；阈值前、恰好等于阈值、超过阈值分别验证，组合折扣沿用原逻辑。
8. 原请求透传和其他处理器日志测试继续通过。
9. 已触发长上下文时，档位输入、输出及缓存价格确实参与计算；部分配置按项回退，不能在长上下文分支重新用原模型价格覆盖已命中的档位价格。
10. 相同长上下文用量，priority / flex / default 按第 5 节分别得到 `4760 / 995 / 2140`；缺失档位与 default 同样按原模型计费，但日志事实字段不同。
11. 日志中的价格参数与长上下文系数能复算最终费用；输入及缓存只乘一次输入系数，输出只乘一次输出系数。
12. 流中先 priority 后 default，最终使用原模型单价并记录 default；兼容上游返回非官方写法 `Standard` 时仍查 `_Standard`，不与官方 Standard 对应的 `default` 混同。
13. 为 `模型_default` 人为配置与原模型差异明显的输入、输出和缓存价格，分别验证普通及长上下文请求均忽略这些配置；日志仍保留上游返回的 default。
14. 当前 9 个已注册长上下文模型保留原边界行为；`gpt-6-astra`、`gpt-6.1-sol`、`gpt-6-sol`、`gpt-6-luna` 及用于测试的后续主版本样例，在 `271999 / 272000 / 272001` 边界分别返回 `1/1、1/1、2/1.5`，不以档位配置是否命中为条件。
15. 价格 getter、已有阈值项目、模型名称、别名及映射后的基础计费模型选择方式不变；精确阈值优先于 GPT-6+ 默认规则，其他未注册模型不自动启用长上下文。
16. priority/fast/flex/ultrafast/default/缺失档位分别验证价格来源；基础模型只用于原阈值查询，拼接键只用于查价。
17. 对已有长上下文模型及新增 GPT-6+ 模型，使用含缓存的总输入超过阈值、扣除缓存后未超过阈值的样例，仍应触发；总输入未超过但输入加输出超过阈值的样例不触发。超过阈值后全量应用系数，计算和日志保持一致。
