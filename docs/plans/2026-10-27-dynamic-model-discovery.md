# 对外模型发现使用实际渠道配置

## 背景与目标

用户已确认排查结论并授权拉取 ezlinkai 仓库修复。线上 `/v1/models` 返回启动时从适配器汇总的静态目录，后台渠道新增的 Gemini、Argon 或自定义模型不会出现在目录中，导致 linkinfra 获取上游模型时遗漏。

## 方案设计

- `model/ability.go`：新增按用户分组查询实际可用模型的函数，关联 channels，过滤未启用渠道、未启用或自动禁用的能力、空模型，去重并排序。
- `controller/model.go`：`ListModels` 和 `RetrieveModel` 共用动态目录；从鉴权上下文的用户 ID 查询分组，保留已有模型元数据，为自定义模型生成兼容的元数据。查询失败返回错误，不回退静态目录。响应禁止共享缓存。
- `router/model_discovery_test.go`：通过生产路由、真实 TokenAuth 和内存数据库验证新增模型、别名、权限、去重、状态更新、空列表及失败行为。
- 保留 `/api/models` 的静态推荐目录；本次不新增 Gemini 路由，linkinfra 已支持从 404 回退至 `/v1/models`。

## 影响范围

对外模型列表从全平台内置目录变为当前用户分组实际可用的模型。已配置的自定义 ID 原样返回，未配置或禁用的模型不再列出。单模型查询采用相同可见性规则，保留原有未找到响应形状及 HTTP 状态。无数据库迁移，不修改价格、调用转发或线上配置。

## 验证方式

先验证回归用例可在原实现上复现遗漏，再验证修复后通过。覆盖新模型和映射别名、重复能力、跨分组、禁用渠道/能力、孤立能力、动态新增和禁用、内置元数据、空列表及数据库故障。执行专项测试、`go build ./...` 和 `go vet ./...`。
