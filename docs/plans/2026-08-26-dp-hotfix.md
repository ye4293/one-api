# dp-fixes 上线后 hotfix：context 泄漏 + 同分排序 + 存量兜底探索

## Context

`dynamic-priority` 分支 5 个 commit（`eb5eb5c → 8703fc0`）今日 13:36 CST 全量部署完毕，通过 Grafana Loki + 生产 DB（`ezlinkai3`）+ AWS ElastiCache（`channel_recent_429:*` / `ability_metrics:*` scan）交叉验证，暴露三个必修问题：

1. **Loki 日志**：`ability metric ZAdd/Expire error: context canceled` 和 `record rate limit ZAdd/Expire error: context canceled` 大量出现 —— 异步 goroutine 用 `c.Request.Context()`，HTTP 响应后 gin cancel 导致 Redis pipe.Exec 失败。
2. **DB 对比**：部署前 1.5h 活跃 channel 108 / 活跃 (channel, model) 对 207 → 部署后 1h 活跃 channel 73 / 154 = **-32% / -26%**。存量 dp=0 老渠道（>24h TTL）被永久冻结在 dp=0 死循环里（无流量 → 无 metrics → 无 dp → 无流量）。
3. **dp 同分 top X% 排序 bug**：`claude-opus-4-8` 8 个 dp=25 同分渠道，`created_time DESC` 强行切开只留 2~3 个，`14417`（weight=100 VIP）被挤到第 8 位靠重试链拿 17%（应有 58.8%）。

用户已选方向：**放宽 TTL + 探索概率化**（非定时探针任务、非全局关阈值）。

## 方案

### (a) 修 context 异步打点丢失

**问题**：`go recordClaudeConsumption(ctx, ...)` 与 `go processChannelRelayError(ctx, ...)` 用 `c.Request.Context()`，Gin 写完响应后 cancel ctx，goroutine 里 `pipe.Exec(ctx)` 立即失败 → 打点丢失。

**修法**：调用异步 goroutine 前把 ctx 换成 `context.WithoutCancel(ctx)`（Go 1.21+，本项目 go 1.25.0 支持）。保留 request-id 等 value 传播，只断开 cancel 信号。

**点位（模式化处理）**：
- `controller/relay.go` — 约 30 处 `go processChannelRelayError(ctx, ...)`（Relay / RelayVideo / RelayGemini / RelayClaude / RelayOcr / RelayRecraft 等多个入口，分布在 line 181, 287, 295, 299, 1091, 1172, 1176, 1388, 1449, 1453, 1760, 1821, 1825, 1900, 1999, 2198, 2274, 2401, 2464, 2590, 2688, 2994, 3084, 3088, 3159, 3249, 3253, 3325, 3416, 3420）
- `relay/controller/claude.go:182` — `go recordClaudeConsumption(ctx, ...)`

**统一封装**：新增 `common/helper/context.go`（或复用已有 helper 包）导出一个短函数：

```go
// DetachCancel 返回一个断开 cancel 但保留全部 value 的派生 context。
// 用于异步打点/日志/quota 更新等 —— HTTP 响应后 gin 会 cancel 原 ctx，
// 直接传原 ctx 会让下游 Redis/DB 操作报 "context canceled"。
func DetachCancel(ctx context.Context) context.Context {
    return context.WithoutCancel(ctx)
}
```

调用点统一改成 `go processChannelRelayError(helper.DetachCancel(ctx), ...)`。集中封装是为了：后续如果需要额外注入 timeout / logger，只改一处。

**审计范围**：只处理上述 dp / 打点相关点位。其他 `context.Background()` 已用的地方（`relay/controller/directvideo*.go` 等）保持不动。

### (b) top X% 保留 dp 同分并列

**问题**：`model/cache.go:665-672` 的 mainTier 组装：
```go
topCount := len(pool) * thresholdPct / 100
mainTier = pool[:topCount]  // 边界 pool[topCount-1] 和 pool[topCount] 同分时强行切开
```

**修法**：切分后往后扫，把与 boundary 同分的渠道一起纳入：

```go
topCount := len(pool) * thresholdPct / 100
if topCount < 1 { topCount = 1 }
if topCount > len(pool) { topCount = len(pool) }
// 保留并列：向后扫，把 dp 相等的渠道也纳入 mainTier
boundaryDp := pool[topCount-1].Dp
for i := topCount; i < len(pool); i++ {
    if pool[i].Dp == boundaryDp {
        topCount++
    } else {
        break
    }
}
mainTier = pool[:topCount]
```

同样修 tier 兜底路径（`model/cache.go:722-731`，`if len(tier) == 0` 分支里的 `pool[:topCount]`）。

**展示层**（`controller/dynamic_priority_view.go`）不改：它是排序展示，不涉及 top X% 切分。

### (c) 存量 dp=0 兜底探索：TTL 放宽 + 探索概率化

**配置层**（`common/config/config.go` + `model/option.go`）：
- `DynamicPriorityExplorationTTLHours` 默认值 `24 → 720`（30 天），旧行为可通过 option API 恢复
- 新增 `DynamicPriorityExploreRatio int = 5`（百分比），0 表示关闭

**选渠道层**（`model/cache.go` tier 组装后、加权计算前）—— **直接 return + Round-robin 共享游标**：
```go
if len(excludeIds) == 0 && skip == 0 &&
   config.DynamicPriorityExploreRatio > 0 &&
   len(unscored) > 0 &&
   rand.Intn(100) < config.DynamicPriorityExploreRatio {
    // Redis INCR 全局共享游标（多节点共享），失败降级到本地 atomic counter
    var seq int64
    if common.RedisEnabled && common.RDB != nil {
        pipe := common.RDB.Pipeline()
        incrCmd := pipe.Incr(ctx, "dp:explore_cursor:"+model)
        pipe.Expire(ctx, "dp:explore_cursor:"+model, 24*time.Hour)
        if _, err := pipe.Exec(ctx); err == nil {
            seq = incrCmd.Val()
        } else {
            seq = exploreRRLocalCounter.Add(1)
        }
    } else {
        seq = exploreRRLocalCounter.Add(1)
    }
    idx := int((seq - 1) % int64(len(unscored)))
    picked := unscored[idx]  // unscored 按 created_time DESC，idx=0 是最新的
    ch := picked.Channel
    return &ch, -1, nil
}
```

**为什么必须直接 return 而不是塞进 tier 走加权**（code review 修正）：
- 加权公式 dp=0 渠道 w=normW(1~10) vs dp>0 渠道 w=normW×dp(25~1000)
- 若塞进 tier 只有约 1% 被抽中，5% 触发 × 1% 打中 = **0.05% 有效流量**
- 完全达不到"给存量老渠道兜底"的目标 —— 探索位形同虚设
- 直接 return 让 5% 请求真的打到探索渠道，样本进入正常评分链路

**为什么 Round-robin 共享游标而不是随机采样**：
- 随机采样有方差：某个 unscored 渠道有低概率**连续几百次探索都没被选中**，形成"运气型死循环"
- Round-robin 保证**每 len(unscored) 次探索每个渠道被覆盖 1 次**（确定性打破死循环）
- Redis INCR 全局共享游标：多节点通过同一个 counter 推进，聚合公平（不像各节点独立随机会有系统性偏差）
- Redis 挂掉时降级到进程本地 atomic counter，仍然是 round-robin，只是各节点游标独立

**为什么用 counter 而不是 ZSet 同步 unscored**：各节点的 unscored 数组来自同一个 DB 的同一个 SQL，本质上一致，无需额外 Redis 结构同步。只需要 counter 共享 = 90% 效果 × 10% 复杂度。

**为什么从 unscored[0]（最新）开始**：unscored SQL 已按 `created_time DESC` 排序，unscored[0] 是最新的渠道。运维加渠道时期望"越新的越先验证" —— 符合直觉。

**语义**：
- K slot（默认 2）覆盖"新加入 30 天内"的冷启动探索
- ExploreRatio（默认 5%）Round-robin 覆盖存量老 dp=0 渠道兜底
- 两个机制**独立**：K slot 影响 tier 组成，ExploreRatio 直接短路返回

**副作用**：概率化探索绕过 429 秒级降权和加权公式 —— 但只有 5% 概率、且是"故意采样"，可接受。日志记录 `dynamic priority: probabilistic exploration selected channel #X (rank=Y/Z, seq=N)`。
