# OpenAI 响应缓存创建计费

日期：2026-11-06。

## 范围

保留可配置的 30m/12h 缓存创建价格，在原响应处理流程已经取得的 usage 上计算创建费用，并扩展 `other.usageDetails`。用户要求原有功能保持原样。

请求转换、模型映射、流式转发、usage 获取和过滤、重试、token 估算、Responses 事件处理保留原流程。根据用户补充要求，Chat 请求结构增加三个可选缓存参数，保证客户端传入的值在请求重建后仍可透传。价格配置继续使用原接口；缓存新价格独立于原服务档位选择。不自动注入缓存参数，不主动补取 usage，不依据请求 TTL 推断用量。

## Chat 显式缓存参数透传

OpenAI 兼容 Chat 请求支持透传客户端提供的 `prompt_cache_options`、`prompt_cache_key`、`prompt_cache_retention`。请求结构以 `json.RawMessage` 保存它们，避免模型映射、`max_tokens` 转换、已有 `max_completion_tokens` 或音频流式请求重建时丢失缓存控制字段。

- `prompt_cache_options` 保留整个 JSON 内容，包括客户端传入的 `mode`、`ttl`、`prewarm` 及扩展字段；不限制上游扩展，不修改数值精度。
- 字段缺失时不发送；显式 `{}`、空字符串、`null` 保留原值。网关不默认启用缓存，也不补充模式、时长或预热设置。
- `messages[].content[]` 中的 `prompt_cache_breakpoint` 沿用原消息内容透传，回归验证请求重建后仍保留。
- 流式 `include_usage` 继续遵循原请求转换规则。缓存参数不会触发额外的 usage 请求、响应过滤或基于 TTL 的用量推断。
- 此能力保证参数到达上游，不保证具体模型接受这些参数或实际创建缓存；上游支持范围及参数校验由对应服务决定。

## 缓存创建费用

Chat 读取 `prompt_tokens_details`；Responses 读取 `input_tokens_details`：

- `cache_write_tokens`：创建总量 W。
- `cache_write_tokens_details.ttl_30m_tokens`：明确报告的 30m 创建量 W30。
- `cache_write_tokens_details.ttl_12h_tokens`：明确报告的 12h 创建量 W12。

普通输入继续按原公式扣除缓存读取和创建总量。只有两档明细均明确报告且 `W30 + W12 = W` 时，才按响应分项计费；不从总量反推 30m。

```text
完整有效明细：
创建费用 = (W30 × 30m配置倍率 + W12 × 12h配置倍率)
         × 原选定 ModelRatio × 原长上下文输入倍率 × 原组合折扣

明细缺失或不一致：
创建费用 = W × CacheWriteRatio
         × 原选定 ModelRatio × 原长上下文输入倍率 × 原组合折扣
```

30m 使用新增配置，未配置时保留原 `GetCacheWriteRatio` 的模型默认值和已有显式档位覆盖；12h 未配置时回退 2.5。配置支持明确零值，删除后恢复默认。两档新增覆盖项不参与 `any/applies`，不能关闭原自动服务档位倍率。自动 Priority/Fast/Flex/Ultrafast 倍率、按次计费、最低额度、Chat 向上取整和 Responses 截断均沿用原规则。

没有明细时沿用旧总量计费。总创建量缺失时，仅在两档均明确报告且通过输入余额校验后，用分项之和补全总量。明细缺一档、为 null、无效或分项之和与总量不一致（无论小于或大于）时，记录错误并回退原创建总量；不推算分项，不改变旧字段校验和计费规则。

## usageDetails

| 字段 | 含义 |
| --- | --- |
| `cache_creation_input_tokens` | 复用旧字段记录 30m 创建量；上线前的旧创建量统一按 30m 解释 |
| `cache_creation_12h_tokens` | 新增，明确报告的 12h 创建量 |
| `cache_creation_total_tokens` | 新增，校验或补全后的创建总量 |

2026-11-07 按用户确认的兼容口径调整：不再写入 `cache_creation_30m_tokens`。有效分项时，旧字段保存实际 30m 数量，总量等于旧字段加 12h 数量；只有旧总量或分项不一致而回退时，旧字段记录原创建总量，12h 为 0，总量为原创建总量。这是日志的兼容解释，不改变拆分校验或扣费公式，也不从请求 TTL 推算数量。

有创建量或上游明确报告有效零分项时写入两个新增字段；仅有 12h 创建时，旧字段明确写入 0。没有缓存创建信息时沿用原省略规则。其他 API 的旧日志保持原结构，历史数据库记录不回填，数据库表结构不变。读取历史 OpenAI 账单时，旧字段作为 30m 数量，缺失的 12h 视为 0，总量可回退到旧字段。

`billingDetails.cache_write_tokens` 继续记录计费使用的创建总量；前端分别显示 30m、12h 和总量，即使 30m 等于总量也不隐藏。可识别的 GPT/o 系列旧账单按 30m 标注，其他模型的旧标签保持原样。

## 缓存价格快照（2026-11-07 补充）

根据用户补充要求，有效 OpenAI 缓存分项按 token 结算时，在现有 `other.billingDetails` 追加 `cache_write_30m_ratio`、`cache_write_12h_ratio`，记录本次实际参与计算的相对倍率，显式零值也保存。旧 `cache_write_ratio`、`cache_creation_ratio` 继续表示 30m/总量回退倍率，不改成混合平均价。

Responses 的计算函数返回两档价格快照，有效分项无论是否命中服务档位都传给异步记录函数，普通输入、输出、读取也复用同一次计算的价格。Chat 直接使用结算局部变量，有效分项的读取倍率不在扣款后重新取价。计算公式、取整、预扣、实际扣款、服务档位选择均保持原样。

固定价格的 Chat、非 OpenAI API、无完整有效分项的响应不添加两档快照；没有快照的旧记录不按现价补填。前端账单详情直接展示落库的两档倍率，缺失时不显示，零价显示为 `0×`。历史账单若原本未记录 12h 价格，不能从当前配置可靠恢复。

## 原处理流程的边界

上游没有返回 usage、Chat 缺少有效总 token，或 Responses 仅返回原流程不采集的中间/未完成事件时，继续使用原来的估算和事件规则。此版本不为缓存创建改变这些条件。

## 验证

验证 Chat/Responses、流式/非流式的分项费用及日志；验证旧字段的 30m 语义、无明细回退、非法明细、零值、重复累计快照、原估算和事件处理；回归原价格、服务档位、按次计费、长上下文及组合折扣测试。

## 价格配置与保存

- 原 JSON 设置 `CacheWriteRatio` 和 `CacheWrite12hRatio` 恢复读取/保存；原 GPT 价格编辑字段 `cache_write_30m_ratio` 和 `cache_write_12h_ratio` 恢复支持。
- 30m 新配置使用独立的运行时映射，不修改历史 `CacheWriteRatio`，避免新增的 `_priority` 等价格键触发整档费用继承切换。非 OpenAI API 的原创建倍率也不受新配置影响。
- 有档位缓存配置时只覆盖对应创建费率；普通输入、输出、读取、自动档位倍数及按次计费规则保持原样。
- 单模型保存基于数据库中的最新 JSON 合并。同一配置行在事务内加锁，多实例更新不从各自的旧运行时快照覆盖其他模型。
- 新缓存选项的保存及同步在本实例内串行，提交成功后才发布到 OptionMap 和计费 getter。其他 Option 更新流程不变。
- 只增加两个缓存配置项，不引入跨价格项事务。JSON 整表保存仍表示完整替换；单模型保存表示合并对应项。
