# 流式中断持久化进数据库

- **日期**: 2026-07-28
- **计划类型**: 数据可观测性改造（含可选 DB schema 变更）
- **触发规范**: 跨 3 个以上文件 + 涉及数据库字段 → 依 `CLAUDE.md` 强制出计划文档

---

## 1. 背景与目标

### 背景
客户《供应商计量计费能力应答表》条目 1 要求：客户端主动断开/取消请求后，服务端需**及时感知并留存记录**，且能**通过请求 ID 查询中断记录**。

当前代码核实结论（`main` 分支）：
- **感知已具备**：原生 Claude / Gemini / OpenAI-Responses 路径通过 `relay/helper/stream_scanner.go:288-290` 主动监听 `c.Request.Context().Done()`，感知到断开后置 `info.StreamStatus.SetEndReason(client_gone)`。
- **持久化缺失（核心问题）**：
  - `client_gone` 仅存于**内存对象** `StreamStatus` 及**应用运行日志** `logger.Info(c, "client disconnected")`（`stream_scanner.go:290`）。
  - 将流状态写入数据库的唯一函数 `util.AppendStreamStatusOther`（`relay/util/stream_status.go:137`）**全仓库仅在 `relay/controller/helper.go:369`（通用 OpenAI 路径）被调用一次**。
  - 而真正会设置 `client_gone` 的三条原生路径，落库时**均未追加** streamStatus：
    - `relay/controller/claude.go:248`（`recordClaudeConsumption`）
    - `relay/controller/gemini.go:467`
    - `relay/controller/opeai_response.go:215`
  - 通用 OpenAI 路径虽调用了 `AppendStreamStatusOther`，但其流式用旧 `StreamHandler`（`relay/channel/openai/main.go`），**不设置 `client_gone`**（此时 `StreamStatus` 为 nil，函数原样返回）。
- **净结果**：被中断请求的消费日志（`Log` 表）虽带 `x_request_id` 索引，但**不含任何中断标记**，无法区分「正常结束」与「客户端中断」；`/api/log` 管理接口无法按请求 ID 查出「已中断」状态。

### 目标
1. **主目标（必做）**：让已感知到的流式中断（`client_gone`，以及 `timeout` / `scanner_error` / `panic` / `ping_fail` 等异常结束原因）**结构化持久化到 `Log` 记录**，实现「按 `x_request_id` 查到该请求 → 可读出结束原因」。
2. **增强目标（可选）**：支持「批量筛选所有被中断的请求」（按结束原因过滤查询），需独立字段 + 索引。
3. **扩展目标（可选、后续）**：让旧 OpenAI/Anthropic 兼容路径的流式也能感知并记录中断（当前该路径不监听 context）。

## 2. 方案设计

分三个递进阶段，阶段一无 schema 变更、风险最低，建议先落地。

### 阶段一：三条原生路径补写 streamStatus（无 schema 变更，必做）

复用现有 `Log.Other` 字段的 `streamStatus:{...}` JSON 段承载中断原因。改动为在三处 `RecordConsumeLogWithOtherAndRequestID` 调用**之前**，对 `other` 变量追加一行：

```go
other = util.AppendStreamStatusOther(other, meta.StreamStatus)
```

涉及文件与插入位置：
| 文件 | 落库调用行（以 grep 为准，实施前需再核对） | 变量名 |
|---|---|---|
| `relay/controller/claude.go` | :248 前 | `other` |
| `relay/controller/gemini.go` | :467 前 | `other` |
| `relay/controller/opeai_response.go` | :215 前 | `other` |

前置确认：三个 `record*` 函数是否都能访问到 `meta *util.RelayMeta`（`StreamStatus` 挂在其上）。`claude.go:197 recordClaudeConsumption` 签名已含 `meta`；`gemini`/`opeai_response` 的记录函数需确认签名同样持有 `meta`，若无则需透传。

**效果**：断开/超时/异常结束的请求，其 `Log.Other` 将包含
`streamStatus:{"status":"error","end_reason":"client_gone","end_error":"context canceled"}`。
按 `x_request_id` 查到该行后即可解析出中断原因。

**注意**：`stripAdminInfoFromLogs`（`model/log.go`）对用户侧接口会剥离 `Other` 中的部分字段，需确认 streamStatus 段是否应对普通用户可见；若客户对账走用户维度接口，要保证该段不被误剥离。

### 阶段二：新增结构化字段 `end_reason`（DB schema 变更，可选增强）

若客户需要「一键筛出所有中断请求」，`Other` 里的 JSON 不便高效过滤，需独立列：

1. `model/log.go` 的 `Log` struct 新增：
   ```go
   EndReason string `json:"end_reason" gorm:"type:varchar(32);index:idx_end_reason"`
   ```
2. `RecordConsumeLogWithOtherAndRequestID` 增加 `endReason` 入参（或从传入的 `StreamStatus` 内部提取），写入该列。
3. `controller/log.go` 查询接口增加 `end_reason` 过滤条件（类比现有 `x_request_id` 过滤）。

**DB 迁移（严格遵守 `CLAUDE.md` 数据库禁令）**：
- **仅允许 `ALTER TABLE logs ADD COLUMN end_reason VARCHAR(32);`（新增非主键列）**。
- GORM `AutoMigrate` 通常会自动加列；但**须由用户确认**是否在生产库执行，或提供手动 SQL 由用户决策。
- **严禁**任何 DROP / TRUNCATE / 无 WHERE 的 DELETE。

### 阶段三：旧兼容路径感知中断（可选、后续）

让 `relay/channel/openai/main.go` 的旧 `StreamHandler` 与 Anthropic 兼容流式也监听 `c.Request.Context().Done()` 并设置 `StreamStatus`，使 OpenAI 兼容渠道的中断同样可被记录。改动较大、影响面广，**本次不实施**，仅登记。

## 3. 影响范围

| 维度 | 阶段一 | 阶段二 | 阶段三 |
|---|---|---|---|
| 涉及文件 | claude.go / gemini.go / opeai_response.go（各 +1 行） | + model/log.go、controller/log.go | + openai/main.go、anthropic/main.go 等 |
| DB schema | **无变更** | 加 1 列（需用户确认） | 无 |
| 对现有计费 | **无影响**（仅写 Other 附加段，不改扣费金额） | 无影响 | 无影响 |
| 对现有日志读取 | 兼容（Other 追加段，旧解析忽略即可） | 需注意用户侧字段剥离 | 兼容 |
| 数据迁移 | 不需要 | 仅加列，历史行该列为空 | 不需要 |
| 回滚 | 删除新增行即可 | 列可保留（不删列） | 代码回退 |

风险点：
- 阶段一唯一风险是 `gemini`/`opeai_response` 记录函数若未持有 `meta`，需先透传 `StreamStatus`，属小范围签名调整。
- 非流式客户端中断（应答表条目 9）本方案**不覆盖**——非流式当前根本无法感知断开，属独立议题。

## 4. 验证方式

1. **编译与静态检查**（提交前必跑）：
   ```bash
   go build ./... && go vet ./...
   ```
2. **单元测试**：`relay/util/stream_status_test.go` 已覆盖 `AppendStreamStatusOther` 各分支；阶段二新增字段需补 `RecordConsumeLog` 写入/查询用例。
3. **手动端到端验证**（阶段一）：
   - 发起原生 Claude/Gemini 流式请求，客户端中途 `Ctrl-C` / 关闭连接。
   - 查 `logs` 表该请求行（按 `x_request_id`），确认 `other` 含 `streamStatus:{...,"end_reason":"client_gone"}`。
   - 对照正常完成的请求，确认其为 `end_reason:"done"` 或无 error 状态，两者可区分。
4. **计费不变回归**：对比中断前后 `quota` 扣费金额，确认改造未影响计费口径（预期：金额不变，仅多出中断标记）。
5. **超时场景**：构造 `STREAMING_TIMEOUT` 内无 chunk 的场景，确认落库 `end_reason:"timeout"`。

## 5. 与应答表的对应

落地阶段一后，应答表**条目 1「留存记录」**可由「仅应用日志、不可按请求ID查」升级为「结构化落库、可按 `x_request_id` 查出中断原因」，条目 1 整体应答具备从「部分支持」上修的依据（限原生 Claude/Gemini/OpenAI-Responses 渠道）。
